# Architecture rules
- WhatsApp instance reads use explicit non-secret column grants, including alert settings; new readable columns need matching grants so credential protection does not break the list.
- Manual transfers use one authenticated database transaction shared by Kanban and Conversations; this keeps client, lead and audit assignments consistent without broadening direct table permissions.
- Project dialogs require the parent record's seller ID from each caller and use it for new inserts; this prevents session roles from overriding the responsible seller.
- Lead editing stage options derive from KANBAN_STAGES and preserve the existing lost state when applicable; this prevents valid board stages from rendering blank or being erased during unrelated edits.
- ERP client searches use a bounded request budget and propagate transport/provider failures separately from successful empty results; this avoids reporting an unavailable ERP as a missing client.
- ERP name search caches only a query template that returned clients, and the quote form falls back to CRM clients and leads when the ERP finds nothing or fails; this keeps one empty-but-accepted template from hiding clients and lets sellers proceed while the ERP is down.
- Dialog and AlertDialog bases cap their height to the dynamic viewport (dvh, with a vh fallback) and scroll internally, and the app shell uses dvh; this keeps long modals and page bottoms reachable on mobile browsers whose toolbars shrink the visible area.
- Seller filters (SellerCombobox) hide operators inactivated in Admin (is_active false or status "inactive") while keeping an already-selected name visible; every seller list passed to it must carry isActive or the raw is_active/status columns.
- Service alert times come from alert_time_settings (seller exception > store > global default > 30/60/90), resolved by src/lib/alertTimes.ts on screen (useCrm().alertTimesFor) and mirrored in the service-alerts function; urgency labels and alert texts must be built from the resolved times, never hardcoded.
- The CRM dashboard keeps only the KPIs and funnel inline; each detailed report is a DashboardPanels card that mounts its report in a popup (?painel=key) on demand, so new reports go into the panels list instead of being stacked on the page.
- External-team card fields (city, segment, last contact, next action) live on leads; last contact is advanced by a whatsapp_messages trigger on sent messages and the next action becomes an agenda follow-up through a leads trigger (only when action/date really change), so the app never creates those follow-ups itself.
- External-team qualification answers live in leads.qualification (JSON) and src/lib/qualification.ts (missingForStage) is the single funnel gate, enforced on every forward stage change for external leads (Kanban drag and next-stage button, "venda concluída" closure, EditLeadForm, SuporteOrcamento quote request); moving backward, marking as lost and rescheduling stay free, so new stage-change paths must call the same gate.
- External-team visit routine: per-seller goals live in seller_goals (default 10 planned / 5 done per week, quarterly new clients optional); a week is Monday to Monday by follow-up scheduled date, done means a completed visit follow-up, and a new client is a client's first CRM sale by normalized phone across all sellers (get_new_clients); numbers are scoped by can_view_seller, so new reports must reuse these RPCs instead of recounting in the app.
- Google Calendar sync keeps OAuth tokens in google_calendar_connections with SELECT granted only on non-secret columns and no realtime, so the app must select explicit columns; CRM follow-up changes reach Google only through the follow_ups outbox trigger, and inbound Google changes go through google_calendar_apply_event, which sets app.google_sync for that transaction so they are not echoed back.
- External-team monthly goals live in monthly_goals plus month_business_days (empty means the app's Monday–Friday-minus-holidays count); quoted is the sum of quote PDFs and sold the sum of invoice PDFs in sales_documents by issue date, so goal, conversion and daily-target views must read those documents rather than lead values.
- Quote and invoice PDFs go to the private sales-documents bucket under {seller_id}/ (or stay in pricing_attachments when they come from a support response) and are read by the sales-document-extract function with the existing OPENAI_API_KEY; it only fills empty fields and keeps the raw AI output in ai_extracted, and the person confirms before the document counts.
- Goal and sales panels render inside ProtectedView (viewer watermark, no print or copy) and export only through useCanExport (admin or gerente); new sensitive panels must use both.
- Every sales_documents row starts pending and only counts toward goals after confirmation by an admin or the seller's store manager (guard_sales_document_review trigger; a non-confirmer editing seller, kind, total or date of a confirmed row sends it back to pending); batch imports go to the importacao/ folder with no seller, suggest_sales_document_seller fills the DE-PARA suggestion (seller named in the PDF, learned client_seller_map, client portfolio by CNPJ, card name), and each confirmation teaches client_seller_map.
- Feedback files and operator audio live in the private seller-files bucket under {seller_id}/feedback (PDF, written only by can_manage_feedback: admin or the seller's store manager, never the operator), {seller_id}/respostas (the operator's own reply audio) and {seller_id}/posvenda (post-sale low-rating audio, an alternative to the 20-character note); guard_seller_feedback lets the operator answer once and only managers edit the period, and feedback PDFs are shown only through ProtectedPdfViewer (pdf.js canvas inside ProtectedView, no download link).
- The Show das Tintas ranking comes only from get_quiz_leaderboard (sum of points, optional p_since/p_until for a chosen month, photo from the profile or else the operator record); operator photos set by an admin go through admin_set_user_avatar (profiles only let each user change their own), and the seller's month-by-month evolution is computed from their own quiz_attempts by src/lib/quizEvolution.ts.
